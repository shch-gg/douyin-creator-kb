# 抖音博主知识库

把抖音上的剧情 / 情绪短片创作者，拆成**可逐秒回溯的档案**，再从档案里长出**可复用的规律**。

不是收藏夹，不是影评合集，也不是"拆完就躺"的成品库——它是一条流水线：你丢一条链接进来，库长出一片档案；档案攒够样本，长出知识卡；下一个样本进来，知识卡被支持、收窄或推翻。

当前：**v0.1.0 骨架版**，结构已立，等待首批投料。

## 它和"十一卷反解"有什么不同

十一卷解决的是**单部片子的深度**：一部片子拆到第十卷，够细。
这个库解决的是**跨作品的高度**：20 部片子放在一起，能看出哪些手法是真规律、哪些只是这一部的巧合。

| | 十一卷（旧） | 本库（新） |
|---|---|---|
| 单位 | 一部作品一个目录 | 博主 → 作品 → 4 秒格，三级 |
| 检索 | 靠人翻目录 | `catalog/index.json` 紧凑索引，先读索引不读正文 |
| 结论 | 单部结论，说完就完 | 知识卡，带样本数、反例、边界、版本 |
| 生长 | 拆完即封存 | 新样本强制回查旧结论，支持/收窄/推翻都留痕 |
| 校验 | C5（单部内部） | C5 + 全库一致性（ID/计数/索引/孤儿卡/样本灌水） |
| 谁能接手 | 记得上下文的人 | 任何 AI：跑 `next_task.py` 就知道下一步 |

旧成品**不搬迁、不改写**，作为"档案原文"由 `works/<id>/dossier/` 指针引用。只做三件事：登记指针、抽 profile 字段、把 09 卷转成 `beats.jsonl`。

## 核心设计：4 秒一格

抖音短剧的信息单位不是"章"，是"秒"。而每秒抽帧拼成的 2×2 拼图，一张正好覆盖 4 秒——**拼图格就是天然的原子**。

```jsonc
{"wid":"w-0001","grid":"c-03","t0":8,"t1":11,
 "visual":"许颂低头站在教室后门，暖光从右侧窗打入",
 "sub":"我讨厌童枳",
 "speech":[{"who":"p-0001","text":"我讨厌童枳","t":9}],
 "func":["hook.character"]}
```

一行 = 一格 = 一个动作或一句话。全库几百部片子、上万行，全部可按秒检索。

注意 `sub` 与 `speech` 分开：屏幕上写的字和听到的话**经常不一致**。第三集 63s 屏幕是「怎么他妈就欺负你」，音频里没有「他妈」——混成一个字段就永远查不清。

## 知识怎么长

```text
1 部  → observation 观察    只会说"目前只见于…"
3 部  → pattern 模式        "较可能…，基于 3 部"
6 部  → rule 规律          "可以确认…（6 部 / 3 位博主）"
15 部 → law 定律           跨 3 题材 + 实战复现 1 次
```

**样本按独立作品算，系列 8 集只算 1 部。** 这是防灌水的第一道闸。

升级不许跳级；降级有三种：`narrowed`（加边界）、`refuted`（被反证）、`superseded`（有更强解释）。**一律不删卡**——删掉等于让下一个人再踩一遍。

五个生长入口：新作品、新博主、同博主新集、自己实战的数据反馈、外部对标。每次投料都必须跑"受影响卡"清单，无影响也要留记录。

## 十条命令

```bash
cd /workspace/抖音博主知识库
python3 _pipeline/next_task.py              # 下一步做什么
python3 _pipeline/new_work.py --creator … --title … --aweme …   # 新建作品
python3 _pipeline/prep.py --work works/w-XXXX --src 原片.mp4    # 闸门2 六件套一条命令（--ocr 开 OCR）
python3 _pipeline/backfill.py --apply       # 把既有 11 卷档案回收成 beats（--dry-run 先看解析率）
python3 _pipeline/text05.py --apply         # 把 05 卷权威表解析成 sub/screen（--dry-run 先看条数）
python3 _pipeline/build_index.py --sync-creators                # 作品变了，回写博主计数
python3 _pipeline/build_index.py            # 重建索引（改完必跑）
python3 _pipeline/c5.py w-0001              # 单部作品证据链自校验（交卷前）
python3 _pipeline/validate.py               # 全库体检，0 error 才算干净
python3 _pipeline/selftest.py               # 校验器自测：11 个负向用例全过，才说明闸门是活的
```

顺序是死的：`c5` 先让单部作品自洽，`validate` 再查全库一致。反过来做会查出一堆噪音。

`backfill.py` 是**历史资产通道**：把已经写完 11 卷的旧档案（`01_最终交付/`）解析成库内 beats，状态记为 `backfilled`——意思是「beats 来自档案解析，本库闸门 2 没重跑」。它不是捷径，是让 36 部旧账能参与统计与知识提炼，不必重拆一遍。解析只搬档案原文：`visual` 取 09 卷 c_NN 块正文，`sub` 取行文里的「字幕「…」」，`shot/move/speech/func` 一律留空，因为这些档案里本来就没有逐格结构化字段。

`text05.py` 是**回填的第二棒**：`backfill` 只能从 09 卷行文里抠字幕，05 卷那些结构化表格（ENEMY 的 UI 红字、片名卡、署名卡、招牌）它看不见。`text05` 按 `text05_map.json` 的逐部配方去 05 卷取权威表，把对白写进 `sub`、画面文字写进 `screen`。**不自动猜**——每部作品配一行，找不到节就报 `missing_sections`。

`prep.py` 把闸门 2 的六件套（抽帧/拼图/切点/帧差/四曲线/OCR）收成一条命令。它是**重建实现**（原脚本没留存），坑都写在代码注释里：4 worker×单线程、`det_limit_side_len=480`、拼图缩放后拼 1500 宽。

`selftest.py` 是**校验器的校验器**：它故意造 11 种违法数据（篡改索引、自造标签、状态拼错、计数漂移、缺必填、成熟度越级、区间断裂、修订不全、枚举越界、类型不符、格号位数不对），看每一道闸门会不会红。改了任何脚本都先跑它。

## 边界

- 不是数据平台：没有播放/完播/涨粉曲线时，不编造传播结论
- 不是转录库：只留必要短引 + 秒级事实
- 不是影评：观众评价与作品事实分栏
- 不是一次性的：结论会随样本变化被收窄或推翻
- **没有证据就不写**：回答"有没有 X"前先查 `coverage` 与 `catalog`
